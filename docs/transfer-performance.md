# ファイル転送性能の測定とコピー削減

Worker本文の余剰コピーを省き、Nodeで切り出した1GiB相当の本文処理のCPU時間は平均0.997秒から0.309秒へ約69%減った。実ブラウザの総転送速度・総メモリの安定した改善は確認できていないため、先読みや暗号処理の変更は見送った。

2026年10月29日。ローカルのAstro・Hono・workerd・R2/D1エミュレーターとChromiumで測定した。本番への負荷試験・デプロイは行わない。新たなサーバー側の永続データは追加しない。

## 既存経路はチャンク単位で処理する

```mermaid
flowchart LR
  F[ブラウザのFile] --> R[8MiB読込・AES-GCM]
  R --> P[8MiBパート・並列送信]
  P -->|proxy| W[Worker: 上限検証]
  W --> R2[R2: 暗号文Multipart]
  P -->|direct: 署名URL| R2
  R2 --> G[Worker: bodyを配信]
  G --> B[ブラウザ: Range取得・順序整列]
  B --> D[認証検証・逐次復号]
  D --> S[逐次保存 / Blob]
```

アップロードは `useUploadSession` → `iterateFileChunks` → `iterateEncryptedChunks` → `bufferAhead` → `repartition` → `uploadChunksFromStream` → complete API の順に進む。

- ブラウザは `File.slice().arrayBuffer()` で8MiBずつ読み出す。WebCryptoのAES-256-GCMで暗号化し、IV・タグをパケットへ格納する。先頭の16B salt、チャンク番号、最終チャンク判定をAADに使う。選択時に先頭チャンクを準備し、送信中は最大8チャンクを先読みする。
- 暗号パケットは8MiBのR2パートへ詰め直す。ファイル全量は保持しないが、暗号化・パケット化・パート化にはコピーがあり、先読みと送信中パートは同時に保持される。送信並列数は無料・Standardが8、Premiumが12。
- start APIでセッションを作成する。directモードは署名URL取得→R2 PUT→WorkerへETag ACK、proxyモードはWorkerのchunk API→R2 `uploadPart`。失敗時は同じパートを再送し、direct失敗時はproxyに戻す。completeでR2のパートを結合し、実サイズを検証する。
- proxyは本文を上限8MiBの固定バッファへ読み込み、上限超過を実測で拒否してからR2に渡す。任意長ストリームをそのままR2へ通す方式は、この検証や異常リクエストへの対応を変えるため採用しない。
- 進捗は成功したパートの暗号文バイト数を加算する。再送失敗を二重加算しない。毎ネットワークチャンクのReact再描画は行っていない。

ダウンロードは R2 → Worker Response → `createParallelCiphertextStream` → `iterateDecryptedChunks` → 保存先 の順に進む。

- 通常ファイルは8MiBのRangeを6本並列で取得し、順番を整える。並列取得器内の取得済み・処理中の先行ウィンドウは最大8個に制限する。出力ストリームと復号側の保持分は別にある。各ウィンドウは `arrayBuffer()` で保持するが、ファイル全体を一括取得しない。
- 「1回」共有は単一GETで取得し、回数制御・削除の意味を維持する。WorkerはR2のbodyをResponseへ渡し、必要な経路ではバイト数確認用TransformStreamを挟む。
- 復号器はパケット境界まで蓄積し、1バイト先読みで最終パケットを判定する。GCM認証・AAD・期待サイズで改ざんや切断を検知する。salt/AADなしの旧形式にも対応する。
- 保存先が遅い場合はReadableStreamのpullと書き込みawaitで流量を抑える。復号は1チャンク先読みする。対応環境ではFile System Access APIかService Worker経由で逐次保存する。非対応環境のBlob保存は全平文を保持する。ZIPも逐次保存経路があるが、メモリ内ZIPのフォールバックは全量保持となる。

鍵はURLフラグメントからクライアントのみが取得する。今回もファイル形式・暗号方式・既存URL・D1スキーマ・保存データの種類は維持する。

## 測定環境

Apple M2・24GiB RAM、macOS 26.6.2 arm64、Node v26.7.0、Chromium 156.0.8078.4。実際に使用したパッケージはPlaywright 1.64.0、Vitest 5.0.3、Wrangler 4.149.0。API側Wranglerが使うMiniflareは5.20261006.1-alpha、Astro側は5.20261006.0-alpha、Vitestから直接使うMiniflareは4.20260730.0。作業開始時のmainは `9aa21f0`。

既存node_modulesの一部はpackage.jsonの要求バージョンより古く、`npm ls` はその不一致を報告する。今回の比較では同じインストールを使い、途中の依存更新は行わない。通常E2Eが保持する録画・トレースは性能測定時だけ無効化する。録画ありの予備測定・途中で中断した試行・設定エラーで起動しなかった実行は最終表に混ぜない。専用実行内の転送失敗は成功率の母数に含める。

## 同じ条件で再測定する

```sh
# 全サイズ（1 / 10 / 100 / 500 / 1024 MiB）、各3回、逐次実行
TRANSFER_BENCH_LABEL=before npm run benchmark:transfer
# 修正後に別ラベルで実行
TRANSFER_BENCH_LABEL=after npm run benchmark:transfer
# サイズ・試行数の限定
TRANSFER_BENCH_SIZES=100,500 TRANSFER_BENCH_TRIALS=1 TRANSFER_BENCH_LABEL=check npm run benchmark:transfer

# ネットワークを除いたコピー処理の切り分け
npm run benchmark:packet
npm run benchmark:upload-body
```

MB/GBの曖昧さを避け、既存テストに合わせてMiB/GiBで統一する。1024MiBは1GiB。合成ファイルは1MiBずつディスクへ生成する。送信者と受信者は別のBrowserContextを使う。匿名の無料プラン、保存期間1日、パスワードなし、proxy転送、1ファイルずつの条件とした。通信はloopbackで帯域制限なし。Turnstileは既存ランナーの公開テストキーを使う。ベンチマークでは `showSaveFilePicker` を無効にし、ブラウザの通常ダウンロード経路を測る。OSの保存ダイアログを伴うFile System Access APIの測定ではない。保存後にサイズとストリーミングSHA-256を照合する。テスト用の既存D1/R2レコード・入力・保存ファイルはランナーの一時領域に作成し、終了時に削除する。

ベンチマークは既存のローカル隔離ランナーでのみ実行可能。本番を既定URLにする通常の `test:e2e` から直接実行しない。結果は `tmp/transfer-benchmark-<label>.jsonl` に追記する。同じラベルを再使用すると既存結果も残るため、集計時は対象試行を区別する。JSONには鍵・共有URL・本文・ファイル名を記録しない。

アップロード時間は送信ボタン操作から完了statusまで。選択時の先頭暗号化準備は含まない。ダウンロード時間は保存ボタン操作からPlaywrightの `download.saveAs` 完了まで。ローカルのテスト出力先へのコピーを含み、SHA-256照合・受信ページ表示・ファイル生成時間は含まない。Playwrightの操作・待機の固定費も含むため、小容量ほど測定制御の影響が大きい。速度は平文MiB÷所要秒で計算する。純粋な回線速度やR2単体の速度とは異なる。

CDPを約50ms間隔で採取する。JSヒープとbacking storage（ArrayBuffer等）は別々の採取時ピークを記録し、足し算して同時ピークと扱わない。ブラウザ全体・Service Worker・ネットワークプロセス・workerdのメモリは含まない。短時間の割当は取り逃がす場合がある。TaskDurationはページrendererのタスク処理時間であり、WebCryptoの全CPU時間やWorker CPUではない。

コピー用の2スクリプトはNode/Viteで実関数を読み込む局所測定。各サイズを8MiB以下の断片で処理する。暗号化・ネットワーク・R2・ディスク保存の時間を含まない。`peakExternalBytes` は各反復後のNode外部メモリの最大観測値、`maxRssKiB` はVite起動と前のサイズを含むプロセス生存期間のhigh-water markであり、当該サイズだけのピークではない。起動・ウォームアップ後のGCを各サイズの直前に実行する。GC中・コピー内部の瞬間的なピークは未測定。

## 採用した変更はWorker本文の余剰コピー削減

`readBodyWithinLimit` は、上限ちょうどの本文を読み終えた場合に固定バッファをそのまま返す。従来の `body.slice(0, totalBytes)` による全量コピーを省く。末尾まで読み、後続の超過バイトを検証する処理は維持する。短い最終パートは従来どおり実データ長に切り詰め、バッファの余白を送らない。受信元の配列からは引き続き独立している。

追加テストは本文の0B・上限未満・上限ちょうど・上限を1B超えるストリームを対象とし、過少なContent-Length申告を信用しないこと、余白を含めないこと、受信元の改変で結果が変わらないことを確認する。

### 先読み削減と復号側の単一コピー化は不採用

先読みキュー8→2、パケット分解の二重コピー→単一コピーも試したが、最終実装には残していない。両方とWorker本文変更を合わせた候補では、100MiB・500MiBの各3試行で総時間が基準より長く、受信のbacking storage観測値も増えた。1GiB測定を始める前に候補の採用を止めた。完了した12試行はすべてSHA-256が一致した。

パケット分解を元に戻した100MiBの切り分けでは、受信のbacking storage観測値が元の水準に戻った。Nodeの局所コピー時間が減っても、ブラウザのGCや実転送時のピークを改善するとは限らない。先読み2の試行でも速度維持を確認できず、8へ戻した。実装を複雑にしてこれらの候補を継続する根拠は得られなかった。

切り分けの一部ではローカルdev ProxyWorkerの `Network connection lost` が発生し、既存リトライによって完了した。100MiBでアップロード112.87秒となった値も除外せず残す。これは本番Cloudflareの失敗を意味しない。同種のkeep-alive境界での失敗は[Cloudflare公式リポジトリのissue #14641](https://github.com/cloudflare/workers-sdk/issues/14641)にも報告されている。ただし今回の原因をそのissueと同一と断定する検証はしていない。[診断の集計](benchmarks/2026-10-29-local-diagnostics.json) のメッセージ数はログ出力の件数であり、失敗リクエスト数とは異なる。

## 測定値の読み方

総時間は完了した測定区間の算術平均、速度はサイズ÷平均秒数、メモリは3試行中の採取時最大値で比較する。失敗率はアップロードから保存後のSHA-256照合までを含む試行の失敗数÷試行数。未完了測定区間は平均時間から除外しても、試行自体は失敗率の母数に残す。未測定値は0に置き換えない。計測機能自体のエラーも試行失敗として記録されるため、失敗が出た場合はネットワーク障害と分けて原因を確認する。

各3回のローカル測定であり、帯域・OSキャッシュ・GC・端末の負荷を完全には固定していない。小さな時間差の因果関係や統計的な優位性は、この測定だけでは断定できない。

### 途中の失敗応答と、ファイル全体の成功率を分ける

最終版の測定区間別API診断値は次のとおり。基準側にはこのカウンタがないため、要求単位の失敗率の前後比較は未測定。

| 区間 | 試行リクエスト数 | 失敗HTTP応答 | transport failure通知 |
| --- | ---: | ---: | ---: |
| upload | 658 | 34 | 3 |
| download | 624 | 0 | 0 |

リトライを含む時間で比較している。総時間はサイズによって増減し、変更していないダウンロードでも差が出た。ローカル環境の変動と途中失敗が混在するため、総転送速度が安定して向上した根拠は得られていない。

直近の100MiB各3回による別の対照比較では、元実装の平均アップロード9.006秒に対し、Worker本文変更のみは8.061秒だった。いずれもAPIの失敗応答・通信失敗は0件。ただし変更していないダウンロードも3.461→3.247秒と動いたため、アップロードの差をすべて変更の効果と扱わない。

network欄は完了した測定区間に対するAPIデータリクエストの診断値。attempts、failedResponses、transportFailuresを分けて記録する。後二者は同じリクエストで重複し得るため、足して転送失敗率としない。測定区間自体が失敗するとその区間はnullとなり、そのnetwork欄も未測定になる。ファイル全体の試行失敗は別のsuccess=falseで数える。

基準測定当時のJSONには保存経路とnetwork欄がない。基準側にも同じChromium・Context設定・capability判定と `verifyRoute` の経路検証を適用しているが、JSONだけから経路を再集計することはできない。最終版では保存経路も記録する。途中で計測指標の未対応判定・エラー時の後片付けを強化したが、成功時の時間境界とCDPコマンド・サンプリング間隔は維持した。

共有E2Eは通信切断・タイムアウト・503・中断と再試行、送信中の再読み込み、期限切れ、R2欠落、同時送受信、マルチパート、Blob保存、キャンセルと再試行、受信エラー・暗号文破損・空レスポンスを確認した。通常E2Eでスキップした性能15件・手動サイズ1件・クロスエンジン1件は別枠の条件付きケース。性能測定では1GiBを含む全5サイズを変更前後に各3回検証済み。

コミット・push・PR作成・本番デプロイは行っていない。

## 制約と次の測定

Cloudflare実環境のRTT、帯域、署名URLとR2直接転送、WorkerのCPU時間・メモリは今回のローカル結果から算出できない。実環境の負荷試験は未実施。Cloudflareは大きな本文の全量バッファリングを避ける設計を推奨している（[公式のベストプラクティス](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/)）。本アプリのproxy本文バッファは既存の8MiB上限を維持する。

帯域制限下の定量比較は未実施。複数利用者の同時転送は既存の耐障害性E2Eで確認する。必要なら専用環境で `E2E_WORKERS=2` を指定したローカルランナーによりベンチマーク試行を同時実行できるが、逐次実行結果と混ぜない。転送の並列数そのものや先読み数は今回変更しない。ネットワーク条件ごとの効果を測らずに増減すると、メモリと実効速度のどちらかを悪化させる可能性がある。

Blobフォールバックは引き続きファイルサイズに比例したメモリを必要とする。実機iOS/Android・OS保存ダイアログ・Firefox/WebKitの性能・低速ディスクへの保存・パケット損失下の性能は別途測定が必要。まず専用の非本番R2とWorkerでdirect/proxyを比較し、先読み量を変える場合はその後に比較する。
