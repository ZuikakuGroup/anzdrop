# 障害検知と復旧のRunbook

更新日: 2026-10-29。対象はAnzdropの運用担当者です。初回は「監視を有効にする」まで確認し、障害時は「通知を受けたら」から参照してください。Cloudflareの管理権限と、既存のAccess認証を使います。

## 既存の計測と今回の改善

公開入口は `anzdrop-router`、画面はAstroの `anzdrop-public`、APIとCronはHonoの `anzdrop` です。D1に共有・認証・分析データ、R2に暗号化済みファイルを保持します。アップロードにはR2への署名付き直接転送もあり、APIだけの正常性では転送成功を保証できません。

| 項目 | 調査結果と扱い |
| --- | --- |
| Workersログ | `withApiHandler`、アカウント認証、個別処理、定期削除に既存のconsole出力あり。API共通ログを構造化し、5xxと5秒以上の遅延に限定 |
| API例外 | 共通ハンドラーは汎用500を返す。Honoの未捕捉例外は以前ログがなかったため、共通観測の対象に追加 |
| フロントエンド | `upload_error` / `download_error` と固定エラーコードを既存の分析APIへ送信。成功率は管理画面のReliabilityで参照できる。汎用の未処理例外収集やSentryは見つからなかった |
| 転送の途中失敗 | ファイル応答後のストリーム切断は既存ログがある。ファイルID、サイズ、例外本文を除去して固定イベントへ変更 |
| D1・R2 | 新しい管理者用ヘルスチェックで、読取APIへの到達を個別確認 |
| 定期処理 | 期限切れ共有・放置アップロードの削除結果とバックログを既存ログに出力。日次分析集計も既存Cronを利用 |
| Cloudflare Observability | 3つのWorkerのWrangler設定に明示的な有効化はなかった。Dashboard側の実設定、通知先、契約プランは未確認 |
| 外部監視 | リポジトリ内に常時稼働する死活監視や障害通知設定は見つからなかった。今回も外部サービスの契約・自動登録はしない |

D1テーブル、分析イベント、Cookie、クライアント識別子の追加はありません。既存の転送計測を再利用します。汎用のブラウザ例外送信は、共有URLや復号鍵の混入を避けるため追加していません。

## APIログから処理と時刻を確認する

`lib/observability.ts` は5xxをerror、5秒以上の応答をwarnで記録します。両方に該当するとerrorを1件記録します。正常なアクセスと通常の4xxは記録しません。全リクエストの分母はCloudflareの標準メトリクスで確認してください。

```json
{"event":"api_request","timestamp":"2026-10-29T00:00:00.000Z","operation":"GET /api/file/:fileId","status":500,"durationMs":42,"requestId":"ランダムなUUID","errorKind":"exception"}
```

`operation` はHonoに登録したルートのパターンです。実際のURL・クエリ・ファイル名・共有ID・アカウントID・IP・認証情報・例外本文・スタックは共通ログに渡しません。`errorKind` は `exception`、明示的な5xxの `server_response`、遅延の `slow_response` です。失敗した依存先を例外文の文字列から推測する処理はありません。

`X-Request-ID` はサーバーが毎回生成します。受信ヘッダーの値は信用せず、利用者識別子と関連付けて保存しません。障害問い合わせでは、このIDとUTC時刻・HTTPステータスを確認します。共有リンクや開発者ツールのHAR全体は受け取らないでください。

`durationMs` はレスポンスのヘッダー確定までです。ストリーム本体の受信・復号・保存完了までの時間は含みません。`download_stream_failed` は応答後の切断、`download_count_restore_failed` は切断後の回数復元失敗を示します。クライアント中断もストリーム切断に含まれるため、単独ではR2障害と判断しません。

## ヘルスチェックはD1・R2の読取を確認する

`GET /api/admin/health` は既存のCloudflare Access認証を要求します。未認証は403で、依存先への確認を実行しません。既存の管理APIと同様に、メールアドレスを含む検証済みAccess JWTが必要です。サービス用トークンへ認可を広げる変更はしていません。

```json
{"success":true,"checks":{"d1":"ok","r2":"ok"}}
```

D1へ `SELECT 1 AS ok`、R2へ予約キー `__anzdrop_readiness_probe__` の `head` を並列実行します。R2にキーがなくてもAPIが応答すれば正常です。利用者データの読み書き、オブジェクト作成、テーブル変更はありません。各処理は3秒で判定を打ち切り、`error` または `timeout` があれば503を返します。Bindingsの処理自体をキャンセルするAPIはないため、タイムアウト後も依存先で処理が続く場合があります。

応答は `no-store` です。これはR2書込権限、D1スキーマ、署名付き転送、復号、決済・メール・microCMSの正常性を保証しません。書込・暗号化・復号を含む確認は、隔離したローカル環境の `npm run test:astro-hono` で行います。本番でテスト共有を作成する場合は、別途データ変更の許可が必要です。

## 監視を有効にする

### Cloudflareの標準メトリクスとMonitorsを優先する

まずDashboardで3つのWorkerのリクエスト数、エラー・例外、CPU時間と実行時間、D1・R2のエラーと使用量を確認します。HTTP 500を通常のResponseとして返した場合、Workerの未捕捉例外数には現れないため、入口のHTTPステータスも併用します。[Workersの標準メトリクス](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/)を参照してください。

CloudflareのAlerts > Monitorsで利用できるデータセットを確認し、Query Builderでプレビューしてから有効化します。データセットと機能は契約・権限に依存します。以下は初期設定の提案で、実測に合わせて調整してください。

| 検出対象 | 条件の目安 | 初動 |
| --- | --- | --- |
| 入口のHTTP 5xx | anzdrop.com、5分で10件以上。利用可能ならリクエスト数100件以上で5xx率5%以上も設定 | 入口とAPP/PUBLICのどちらが失敗しているか確認 |
| Workerの例外・制限超過 | 3つのWorkerそれぞれで5分間に1件以上 | CPU・メモリ・実行制限と直近変更を確認 |
| 遅延 | 全リクエストのp95が5秒超。取得できない場合は `slow_response` の発生を確認 | D1/R2、同時転送、外部APIを切り分け |
| Cronの停止・失敗 | 実行エラーに加え、清掃は7時間、日次集計は26時間を超えて実行がない | リクエスト処理と混ぜずCronの実行履歴を確認 |

[Monitorsの公式手順](https://developers.cloudflare.com/notifications/monitors/)に従い、通知先を選択します。データセットが表示されない場合は、そのプランで利用可能だと仮定しないでください。WorkersログのSQL APIデータセットが使える場合も、リクエストURLやログ本文を通知へ含めず、固定の障害名とRunbookへのリンクだけにします。評価間隔と再通知間隔を分け、再通知はまず1時間を目安に設定します。

### ログ保存は承認後に設定する

今回WranglerのObservability設定は変更していません。永続ログの有効化は、保存する項目・保存期間・アクセス権・料金を確認してから行ってください。共通ログ以外の既存ログには、Stripeのアカウント・契約IDや例外本文、清掃処理の共有IDなどが残ります。これらを監査・除去しないまま全ログ保存を有効にしないでください。

承認後の設定候補は、consoleログのみを対象にし、`observability.logs.invocation_logs` をfalseにして自動的なリクエストURL記録を避ける構成です。自動トレースもURLやSQLの取得範囲を確認するまで有効化しません。[Workers Logsの設定・料金](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)を適用時に再確認してください。ヘッドサンプリングを下げるとエラーも欠落するため、抽出したログ件数を正確な障害率として扱わないでください。全リクエストにログを追加する構成やLogpushは今回導入していません。

### 読取専用スクリプトで死活と転送失敗率を確認する

`scripts/monitor-production.mjs` は依存先の状態、公開トップページ、既存Reliability APIのUTC当日分を読み取ります。公開ページには管理Cookieを送らず、HTTP成功・HTML形式・先頭64KiB内のAnzdropのtitleを確認します。公開画面だけの停止も `public_unavailable` で検知します。ネットワーク要求はそれぞれ10秒で打ち切り、リダイレクトを追いません。HTTP 200でも、想定したJSONとD1・R2の成功結果がなければ失敗と判定します。

環境変数は監視を動かす端末・ジョブ側で設定します。アプリWorkerに新しいSecretは不要です。

| 変数 | 設定内容 |
| --- | --- |
| `MONITOR_BASE_URL` | 確認対象のHTTPS origin。ローカル検証は `http://localhost:ポート` が利用可能。パス・クエリ・認証情報を含めない |
| `MONITOR_ACCESS_JWT` | 既存管理者として発行済みの、メールアドレスを含む有効なAccess JWT。`CF_Authorization` Cookieとして送信。Secretとして管理 |
| `MONITOR_WEBHOOK_URL` | 任意。`{"text":"Anzdrop: 固定コード"}` を受け取れるHTTPS Webhook。Secretとして管理 |

```sh
# 最初は通知なしで検証。環境変数の値をコマンド履歴へ直接書かない。
node scripts/monitor-production.mjs
# 隔離した通知先で検証した後、運用者が明示的に有効化する。
node scripts/monitor-production.mjs --notify
```

通知は `--notify` と障害検出の両方がそろったときだけ送信します。通知モードでは開始時にWebhookの設定を検証し、未設定やHTTPS以外なら要求を送る前に失敗します。成功時の終了コードは0、障害検出は1、設定・通知処理の失敗は2です。標準出力と通知には固定コードだけを含めます。JWT・Webhook URL・APIレスポンス本文は出力しません。

転送の警告条件は当日の成功率90%未満かつ当日のエラーイベント10件以上です。これは分単位の失敗率増加を直接測る指標ではありません。試行中の転送、日付境界をまたぐ転送、分析送信の欠落・遅延、利用者によるキャンセルが影響します。エラー数の最低条件で少数の失敗による通知を抑えています。即時検知はCloudflare側の5xx・例外監視と併用してください。

このスクリプトは永続的な障害状態、通知履歴、復旧状態を保存しません。同じ障害で毎回通知するため、定期実行する場合は実行側で頻度を制限してください。日次の転送率確認は1時間程度を目安にし、ヘルスチェックだけの頻繁な実行と分ける場合は運用設計を見直します。監視を動かす環境そのものの停止は、その外側から監視する必要があります。

**未解決:** 現在のAccess検証は人のメールアドレスを要求するため、通常のAccessサービス用トークンでは自動認証できません。JWTは期限切れになります。無人の常時監視には、監視専用の最小権限認証を別途合意するか、Cloudflare側で認証不要のメトリクス監視を利用してください。認証の緩和や自動更新のための新たな資格情報保存は実装していません。

### 外部監視を追加する場合の比較

| 方法 | 費用・無料枠の確認先 | 運用負担・制約 |
| --- | --- | --- |
| Cloudflare標準メトリクス＋Monitors | 契約画面で対象データセットと評価料金を確認 | 追加ベンダー不要。同一基盤の全域障害で監視も影響を受ける可能性 |
| 既存の端末・ジョブで今回のスクリプト | 新規サービス契約不要。実行基盤の料金、D1/R2の読取回数が増える | JWT更新、実行失敗監視、重複通知への対応が必要 |
| 外部のHTTP死活監視サービス | 無料枠、確認間隔、認証ヘッダー対応、通知回数を契約時に比較 | 別基盤からDNS/TLS/入口の障害を検出できる。秘密を預けるため選定と承認が必要 |

プランや無料枠の未確認な金額は固定値で記載していません。通知先の追加・試験送信・外部契約は今回行っていません。

## 通知を受けたら最初に範囲を確認する

1. UTC時刻と最初の失敗時刻を記録し、Cloudflare Statusと直近デプロイを確認する。成功した最後の時間まで遡って調べる。
2. 入口の5xx・全リクエスト数をWorker別に比較する。APPだけか、PUBLICだけか、全体かを絞る。4xxや単なるアクセス数減少をサービス停止と混同しない。
3. `api_request` を `operation`、`errorKind`、`status` で集計する。問い合わせの `X-Request-ID` があれば対応する1件を探す。保存ログが無ければ今後の再現確認に限定し、過去の原因を断定しない。
4. 管理者用ヘルスチェックを実行し、D1・R2を切り分ける。403やHTMLは監視認証の不備、503は依存先のエラーまたはタイムアウトとして調べる。
5. Reliabilityの転送成功率・エラーコードを確認する。APIが正常でも、署名付きR2転送やブラウザのネットワーク・復号で失敗している可能性がある。

| 状況 | 調査と復旧 |
| --- | --- |
| 5xxが直近リリース後に増加 | Version/Deployment IDを確認し、[デプロイガイド](./deployment.md)の切り戻し手順を検討。ユーザーの許可を得て実行 |
| D1のみ失敗 | CloudflareのD1障害・クォータ・バインディング・マイグレーション状況を確認。データ削除や再作成で対処しない |
| R2のみ失敗 | R2障害・バインディング・アクセス権を確認。署名付き直接転送だけの失敗ではCORS・署名設定も確認 |
| 両方okで転送失敗 | 固定エラーコード、端末・サイズ区分、ネットワークを確認。復号鍵やファイル内容をログへ追加しない |
| `download_stream_failed` が増加 | 利用者中断とR2読取障害を、転送成功率・依存先状態・5xxで切り分ける |
| 清掃のバックログ | 既存の清掃サマリーと失敗数・バッチ上限を確認。無断で保持期間を延長したり手作業で一括削除しない |
| 応答不能 | DNS/TLS、ルーター、サービスBinding、Cloudflare全体障害を順に確認。外部監視からの到達と比較 |
| `analytics_unavailable` / `monitor_failed` | まずAccess JWTの期限・権限、設定、通知先の疎通、実行基盤を確認。監視障害とアプリ障害を分けて記録 |

復旧判断では、ヘルスチェックの正常化に加え、5xxと遅延の低下、実際の利用による転送成功率の回復を確認します。原因、影響時間、影響した処理、対応、再発防止策を残してください。解決しない場合は、機密情報を除いた時刻・固定イベント名・集計値・Deployment IDを添えてリポジトリのIssueへ引き継ぎます。

## 隔離環境で検証する

以下はローカルのVitestとモックだけを使います。本番へアクセスせず、通知処理も偽のfetchで検証します。

```sh
npx vitest run tests/lib/observability.test.ts tests/lib/health.test.ts tests/app/api/admin/health/route.test.ts tests/scripts/monitor-production.test.ts tests/lib/api/handler.test.ts
```

D1・R2の拒否、空のD1結果、ハングと遅延拒否、未認証、503、5秒の境界、同時リクエストの混線防止、ログへの秘密の非混入、誤った200応答、通知の明示有効化、通知先失敗、PUBLICのみの停止・不正なHTML、通知設定不備、90%の境界とダウンロード警告を検証します。本番に障害を注入するコマンドや、通知を送る定期Workflowは追加していません。

## 今回の検証結果

2026-10-29、隔離した作業ツリーで以下を確認しました。

- `npx vitest run --maxWorkers=4`: 160ファイル、1,608テスト成功。
- `npm run lint` と `npx tsc --noEmit`: 成功。
- `WRANGLER_SEND_METRICS=false npm run build:api`: dry-runビルド成功。デプロイなし。
- 独立した検証エージェント: 関連5ファイル34テスト成功。PUBLIC停止の見逃し、通知設定の遅い検証、応答後ログの照合不足という指摘は修正後に再確認済み。

最初の全体実行では共有node_modulesとロックファイルの版の違いがあり、専用に `npm ci --ignore-scripts` で依存関係を導入しました。その後の無制限並列実行では複数の既存テストが60秒でタイムアウトしたため、並列数を4に抑えて全件成功を確認しました。テストのタイムアウト設定や既存機能は変更していません。

本番のDashboard設定、実際の通知配送、Cloudflare上のメトリクス・ログ取り込みは未検証です。適用後に運用者が隔離した通知先で確認してください。

## 用語

- ヘルスチェック: D1・R2の読取APIへ到達できるか調べる確認処理。
- Reliability: 既存のブラウザイベントから転送成功率とエラーコードを集計する管理レポート。
- リクエストID: 1回のAPI要求をログと応答の間で照合するランダムな値。
- Monitors: Cloudflareのデータセットを定期評価して通知する機能。利用可否は契約と権限に依存。
