# SEO・送信導線の改善記録（2026年10月29日）

トップの説明、ブログのcanonical、記事からの送信導線、共有URLの取得方法を修正した。記事が最初の計測対象ページだったセッションでは、記事別に送信成功まで追えるようにした。検索順位や送信完了率の変化は未測定であり、本番デプロイも行っていない。

## 調査範囲と確認できた事実

Astro公開ページ・レイアウト、React送信フォーム、Honoの計測API、既存D1スキーマ・集計、SEO監査スクリプトを確認した。既存の未コミット変更は保持している。以下はコード上の確認結果であり、実利用者の離脱理由を実測したものではない。

| 対象 | 確認結果と対応 |
| --- | --- |
| title・description | トップの一般的な説明を、登録不要・ブラウザ内暗号化・リンク送信という用途に変更。Twitter用タイトル・説明・画像も補完した |
| canonical | ブログ2ページ目以降が1ページ目を指していたため、正規化したページ番号を含むURLへ変更。広告用パラメータはcanonicalへ含めない |
| robots・sitemap | 既存のrobotsは管理・API・マイページを除外。sitemapは公開固定ページとCMS記事・分類・著者を列挙している。変更なし |
| インデックス | 公開ページはSSRのHTMLを返す。ダウンロード画面はnoindex、存在しない記事は404とnoindex。robotsはアクセス制御の代用ではない |
| OGP・構造化データ | 公開レイアウトのOGP、記事のArticle、LPの既存構造化データを確認。トップへWebApplicationを追加。評価点・根拠のない比較は追加していない |
| 内部リンク | 記事末尾に直接送信するリンクと使い方へのリンクを追加。記事の新規生成・公開はしていない |
| ファイル選択 | 選択欄のキーボードフォーカスを可視化し、入力に明確なラベルを追加 |
| 進捗・エラー | 既存の割合表示へprogressbarの意味を付加。エラーをalertで通知し、ファイル選択に戻るボタンを追加。自動再送は行わない |
| 送信完了 | 完了をstatusで通知。共有URLを選択できる読み取り専用入力を追加し、コピーAPI失敗時も手動取得可能にした |
| モバイル | 結果パネルの固定高さを最小高さへ変更。共有URL入力・コピー・復帰ボタンに44px以上の高さを確保 |

ブログのページごとのcanonicalは[Googleのページ分割ガイド](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading)に沿う。Astroは `output: server` とCloudflare adapterを使用し、Reactの `client:load` も初期HTMLをSSRする。[Astroのオンデマンドレンダリング](https://docs.astro.build/en/guides/on-demand-rendering/)も参照した。SSR自体をSEO上の不具合とは判断していない。

公開HTMLはCSP nonceのため既存どおりno-store。画像の寸法、記事アイキャッチの優先取得、著者画像の遅延取得を確認した。React島の数、JS量、レイアウト変動、初期化の負荷はCore Web Vitalsに影響し得るが、今回の変更前後の本番LCP・INP・CLSは取得していない。既存作業に含まれるヘッダー軽量化などは今回の成果に含めない。

## 計測は既存基盤を利用する

依頼されたサービス着地・ファイル選択・開始・成功・失敗・URLコピーのイベントは既存実装に揃っている。新しい分析SDK、D1テーブル、カラムは追加していない。ユーザーの明示許可を得て、記事ページでも既存の `landing_view` を発火するようにした。公開記事パスを既存D1へ保存する。生イベントは1年、既存の日次集計は無期限という保持仕様を変更していない。記事閲覧イベントはファイルのE2E暗号化対象ではなく、既存の分析情報として扱う。

既存のacquisitionレポートはlanding_pathとsession_idを使ってupload_successへ結び付ける。このため、記事別・既存UTM別のセッション数とNew Sender数、および記事着地からファイル選択・アップロード開始・成功・共有へ至るセッション分析が可能になる。ファイル名・内容・共有URL・トークンは追加送信しない。ブラウザ内の共有URL表示も計測ペイロードには含めない。

`landing_view` はセッションで最初の対象ページだけを記録する。全記事PV、記事末尾CTAのクリック率、記事からトップへの全遷移数は測らない。別のLPから記事に移動した場合、最初のLPの帰属を維持する。内部リンクへUTMを付けて外部流入元を上書きすることも避けた。記事追加によってlanding_viewの母集団が広がるため、反映前後の全体ファネルを単純比較せず、landing_pathごとに見る。

## 次に検証する仮説

- 用途を具体化すると、トップ着地からfile_selectへ進むセッションの割合が増えるか。
- 記事末尾の直接導線によって、記事着地セッションのupload_successが増えるか。記事ごとの訪問数と内容の違いも合わせて確認する。
- 手動コピー手段があることで、モバイルで共有リンクを取得できずに止まる利用者が減るか。手動コピーそのものはイベント計測しないため、share_link_copyだけでこの効果を断定しない。
- モバイル・サイズ区分・エラーコード別に、upload_startからupload_successまでの失敗が集中していないか。

本番反映後はSearch Consoleの検索語・表示回数・クリック率・インデックス状況と、既存管理画面のacquisition/funnel/reliabilityを定期間で確認する。少数の訪問による率の変動、再訪、記事追加による母集団の変化を区別する。

## 残る課題

記事ごとのOG画像実サイズとモバイル実機、Search Consoleの登録・実際のクロール結果、本番のCore Web Vitalsは別途確認が必要。汎用のapple-iconを使うページにはSNS用画像の改善余地がある。計測同意UIや任意停止の仕組みは今回追加していないため、既存ポリシーと対象地域に応じた確認も残る。既存UTMは任意文字列を受けるため、機密情報を値に入れない運用を継続する。
