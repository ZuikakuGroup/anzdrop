# E2EE(エンドツーエンド暗号化)の設計

Anzdropの核となる設計方針は「サーバーは平文はもちろん、復号鍵も一度も見ない」ことです。暗号化・復号は常にブラウザの [Web Crypto API](https://developer.mozilla.org/ja/docs/Web/API/Web_Crypto_API) 上で行われ、実装は [`lib/crypto/`](../lib/crypto/) にまとまっています。

## 使用アルゴリズム

[`lib/crypto/types.ts`](../lib/crypto/types.ts) で定義:

| 項目 | 値 |
| --- | --- |
| 暗号方式 | AES-256-GCM |
| チャンクサイズ(平文) | 8 MiB (`CHUNK_SIZE`) |
| IV長 | 12 bytes(チャンクごとに乱数生成) |
| GCM認証タグ長 | 16 bytes |
| ファイルsalt長(AAD用) | 16 bytes (`FILE_SALT_LENGTH`, ファイルごとに乱数生成) |
| パスワード鍵導出 | PBKDF2-SHA256, 600,000 iterations, ソルト16 bytes |

## ファイル本体の暗号化(チャンクストリーミング)

1. アップロード時、ブラウザは `generateKey()` でファイル(共有)ごとに1本のAES-256-GCM鍵を生成する(`lib/crypto/key.ts`)。同じ鍵は、1回のアップロード操作で追加された複数ファイルの間でも使い回される。
2. ファイルを8MiBごとに分割し(`iterateFileChunks`)、チャンクごとに個別のIVで暗号化する(`encryptChunk`, `lib/crypto/encrypt.ts`)。チャンクごとに異なるIVを使うことで、同一鍵での大量データ暗号化によるIV再利用リスクを避けている。
3. 各チャンクの認証タグには、GCMのAAD(Additional Authenticated Data)として「ファイルごとのランダムなsalt(`FILE_SALT_LENGTH`, `generateFileSalt()`)」「そのファイル内でのチャンク番号」「最終チャンクか否か」をバインドする(`buildChunkAad`, `lib/crypto/aad.ts`)。AAD自体は送受信されず、暗号化・復号の両側が同じ入力から独立に再計算して照合する。これにより、R2/D1を操作できる主体(妥協されたサーバーや悪意あるインフラ管理者)が、ストレージ上でチャンクを並べ替える・重複させる・(鍵を使い回す同一share内の別ファイルの)チャンクと差し替えるといった改ざんを行っても、対象チャンクのGCM認証タグ検証が必ず失敗するため検知できる(各チャンク単体の改ざん検知に加えて、ストリーム全体としての順序・完全性も保証する。GitHub issue #1)。
4. 各暗号化チャンクは `IV(12B) + 暗号文 + GCM認証タグ(16B)` の形式でバイナリ化する(`packChunk`, `lib/crypto/packet.ts`)。ファイルの最初のパケットに限り、その直前にファイルsalt(16B, 秘匿不要)を平文のまま埋め込む(`iterateEncryptedChunks`, `lib/crypto/stream.ts`)。
5. R2へのアップロードは、この「salt + 全パケット」のバイト列を、パケット境界とは無関係に `UPLOAD_PART_SIZE`(8MiB, `lib/upload/partSize.ts`)ちょうどで切り出してマルチパートで送る(`uploadChunksFromStream`, `lib/upload/chunkUploader.ts`)。R2は「最終パート以外は同一サイズ」を要求するため、先頭パケットにだけ付くsalt(16B)の分でパートサイズを不均一にしない狙い(パケットごとに1パートにすると3パート以上のアップロードが `complete()` で失敗する。GitHub issue #34)。ストレージ上のバイト列自体は連結結果と同一で、復号側の実装には影響しない。
6. ダウンロード時は逆に、受信したバイトストリームをパケット境界(最終パケットを除き固定長)で切り出しながら、AADを検証しつつ復号し、順次書き出す(`iterateDecryptedChunks`, `lib/crypto/stream.ts`)。ストリームが末尾パケットごと欠落したまま無音に終了するケース(通信切断・改ざんによる切り詰め)は、期待バイト数との比較で検出しエラーにする。

### 互換性(AAD保護導入前にアップロード済みのファイル)

AADの導入(上記3・4)により暗号文フォーマットが変わるため、導入前にアップロード済みの共有中のファイル(salt・AADを持たない旧形式)との互換性が問題になる。`iterateDecryptedChunks` は先頭パケットについて、まず新形式(salt + AAD)として検証を試み、失敗した場合にのみ旧形式(saltなし・AADなし)として読み直すフォールバックを持つため、旧形式のファイルも引き続き問題なくダウンロードできる。新形式のファイルがこのフォールバックを経由して誤って弱い検証をすり抜けることはない(旧形式としての検証も結局はAADなしのGCM認証タグの一致を要求しており、鍵を持たない攻撃者が新形式の認証タグを別の入力で再現することはできないため)。なお、旧形式のまま残っている既存ファイルについては、本対応が防ぐストリーム順序・完全性の改ざんを引き続き検知できない(保存期間切れで自然に旧形式のファイルがなくなるまでの既知の制限)。

このフォールバックは「同じ鍵を共有するファイル群の中に、新形式のファイルと旧形式のファイルが混在することはない」という前提の上で安全である(新形式ファイルのチャンク0の検証失敗を、鍵を持たない第三者が意図的に起こすことはできないため、フォールバックは実質的に「本当に旧形式のファイルである場合」にしか発火しない)。この前提は現状のクライアント実装(1回のブラウザセッション内で生成した1本の鍵を、そのセッションで追加した全ファイルに使い回す。`components/upload/uploadForm.tsx`)では自然に成り立っている。将来、同じ共有・同じ鍵に対して「後から(別セッションで)ファイルを追加する」機能を実装する場合は、その時点でこの前提が崩れないか(=新形式ファイルと旧形式ファイルが同じ鍵を共有し得ないか)を必ず確認すること。

暗号文はサーバー(D1・R2)に渡る前に既に暗号化済みであり、サーバーはIVや暗号文の中身から平文を推測することはできない。ファイル名も同様に暗号化されており、DBには `encrypted_file_name` としてのみ保存される(サーバーは元のファイル名を知らない)。ファイル名の暗号化(`encryptFileName`)やパスワード保護時の鍵ラップ(`wrapKeyWithPassword`)は単一チャンクの暗号化であり、上記のストリーム内チャンク順序に関するAADの対象ではない(そもそも並べ替えの余地がないため)。

## 鍵の受け渡し(URLフラグメント方式)

アップロード完了後の共有URLは次の形になる。

```
https://<host>/d/{shareId}#{復号鍵(base64url)}
```

`#`以降(URLフラグメント)はブラウザの仕様上、サーバーへのHTTPリクエストに一切含まれない。そのためこの方式では、

- サーバーのアクセスログ・エラーログに鍵が残らない
- リバースプロキシ・CDN・アナリティクスにも鍵は渡らない
- ダウンロード画面(`components/download/DownloadPage.tsx`)は `window.location.hash` からクライアントサイドでのみ鍵を取得する

という性質が得られる。`shareId` 自体はURLパス内にあり第三者に露出しうる公開識別子だが、それ単体では復号鍵を持たない第三者はファイルを復号できない(ダウンロード自体は可能だが、意味のある平文は得られない)。

## パスワード保護(任意機能)

パスワードを設定すると、共有のAES鍵そのものを「パスワードから導出した鍵(KEK: Key Encryption Key)」でラップして保存する、二重鍵構造になる。

1. `generateSalt()` でランダムなソルト(16 bytes)を生成。
2. `deriveKeyFromPassword(password, salt)` で PBKDF2-SHA256(600,000 iterations)によりKEKを導出する。導出処理・パスワードそのものはブラウザ内で完結し、サーバーには一切送られない。
3. 共有の実際の暗号化鍵(生の32byte)を、KEKを使って `encryptChunk` + `packChunk`(ファイル本体の暗号化と全く同じプリミティブを、鍵32byteを1個のチャンクとして扱うことで再利用)でラップする。
4. ラップされた鍵(`wrappedKey`)とソルト(`keySalt`)だけをD1の `shares` テーブルに保存する(`migrations/0004_add_password_and_retention.sql`)。

ダウンロード時は `GET /api/download/[shareId]` のレスポンスに `wrappedKey`/`keySalt` が含まれていればパスワード入力を要求し、入力されたパスワードから同じ手順でKEKを導出、`unpackChunk` + `decryptChunk` でラップを解いて実際の鍵を得る。**誤ったパスワードで復号を試みると、AES-GCMの認証タグ検証が必ず失敗して例外になる**ため、「パスワードが違います」の判定は追加の検証ロジックなしにこの例外を捕捉するだけでよい。

この方式のポイントは、サーバーが侵害されて `wrappedKey`/`keySalt`/暗号化済みファイルすべてが流出したとしても、パスワードを知らない攻撃者は総当たり以外にファイルを復号する手段がないこと。パスワード未設定時は `wrappedKey`/`keySalt` ともに `NULL` で、代わりにURLフラグメントの鍵がそのまま使われる(上記「鍵の受け渡し」参照)。

## 保存期間「1回」との関係

保存期間で「1回」を選んだ場合、暗号化・鍵管理自体には影響しない。ダウンロード回数の制御は完全にサーバー側(D1のカウンタ)で行われ、詳細は [`architecture.md`](./architecture.md) の「ダウンロードの流れ」および [`database.md`](./database.md) を参照。

## サーバー側で「見えている」もの・「見えていない」もの

| 情報 | サーバーから見えるか |
| --- | --- |
| ファイルの中身(平文) | ✕ 見えない(暗号文のみ) |
| ファイル名(平文) | ✕ 見えない(暗号化済み文字列のみ) |
| 復号鍵 | ✕ 見えない(URLフラグメントのみ、パスワード保護時はラップ済みの鍵のみ) |
| パスワード | ✕ 見えない(ブラウザ内でKEK導出に使われるのみ) |
| 共有ID・作成/失効日時・ファイルサイズ・ダウンロード回数 | ○ 見える(メタデータとしてD1に保存) |
| アップロード元IP | ✕ 見えない・保存しない(サーバー自身はIPを保持・利用しない。Turnstile検証時に`remoteip`は意図的に送っていない) |

通報フォームで「運営者は共有URLをもとに対象を確認・削除します。ファイルの中身を復号して確認することはありません」と案内しているのはこの設計に基づく。
