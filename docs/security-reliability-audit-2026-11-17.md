# セキュリティ・信頼性・パフォーマンス監査（2026-11-17）

## 対象と方法

開始時のHEADは `15a545d`。既存作業ブランチを起点に `audit/security-reliability-20261117` を作成した。作業開始時の未コミット変更はなかった。リポジトリの構成・設計文書と主要な実行経路を調査し、実害を再現した箇所だけを変更した。全行の形式検証や本番への侵入試験ではない。

データフローは、ブラウザでのAES-GCM暗号化 → Worker経由または署名付きURLでR2へ保存 → D1へ暗号化名・サイズ・期限・アップロード状態を登録 → アクセス期限と停止状態を検証して暗号文配信 → ブラウザで復号・保存。通常の鍵はURLフラグメントに置き、パスワード付き共有ではブラウザで鍵をラップする。Astro公開Worker、API Worker、ルーターはService Bindingで分離されている。

調査対象は次のとおり。

- 認証・認可：セッション世代検証、Cloudflare Access、Origin検証、パスワード・リカバリー、OTPの試行制限と再使用防止、WebAuthnチャレンジの消費。
- 保存・転送：multipart開始/チャンク/署名URL/ACK/完了、暗号文サイズ検査、1回限定配信、HEAD/Range、中断時復元、期限掃除とR2/D1間の障害。
- クライアント：鍵の扱い、暗号化AAD・旧形式互換、ストリームのキャンセルと先読み、ZIP/フォルダ/Blob/Service Worker保存。
- 外部入力と運用：API本文上限、HTMLサニタイズ、CSP、計測のPrivacy Guard、Stripe/OpenNode通知、エラーログ、CIと本番デプロイの分離。

本番API・D1・R2のデータ操作、デプロイ、コミット、push、PR作成は行っていない。新しいテーブル・列・永続情報・依存関係・暗号方式は追加していない。

## 再現して修正した問題

| 重大度 | 問題と実害 | 再現根拠と対策 |
| --- | --- | --- |
| 高 | Bitcoin決済確定後にアカウント更新が失敗すると、再送も処理済みになり購入期間が反映されない | Miniflareの実SQLiteでaccounts更新をtriggerで失敗させ、paymentがpaidのまま残ることを確認。アカウント更新と決済確定をD1 batchで原子的に実行し、どちらの更新が失敗してもロールバックする |
| 高 | 同じアカウントの異なるBitcoin決済が並行すると1回分の購入期間を失う | 2つの決済通知を並列実行し、2回分ではなく1回分しか延長されないことを確認。読取時のプラン・期限を条件にした更新と再計算で、失敗した比較更新は決済確定しない。最大5回競合した場合は500で再送に委ねる |
| 中 | 一括保存の連番名と元の名前が衝突し、ZIPからファイルが欠落する | `a.txt`, `a.txt`, `a (1).txt`から生成したZIPを展開し3件中1件の欠落を確認。発行済みの名前全体で重複判定する。次の連番も記憶し、同名が多い場合の探索増加を抑える |
| 中 | `__proto__`という名前のファイルをメモリ内ZIPへ保存できない | 元実装は空扱いで失敗。null prototype辞書だけではfflate内部でも欠落するため、該当名を含む場合だけ既存のストリームZIP経路でメモリに収集。ZIPの実エントリ名と内容をUnzipイベントで検証。通常の圧縮経路は維持 |
| 中 | レート制限・Stripe処理の例外内容がログへ出る | 合成の機密マーカーを含む例外を注入し、実際のログへ含まれることを確認。固定の操作ラベルのみを記録し、応答・再送・フェイルオープンの挙動は維持。本番での漏洩発生を確認したものではない |
| 低 | 未対応の拡張子 `.constructor` / `.__proto__` にプレビューボタンが出て操作時に例外となる | MIME辞書の継承プロパティも参照していた。2件の再現テストでnullではなく関数・オブジェクトが返ることを確認。辞書自身のキーだけを対応拡張子とする |

D1 batchのトランザクション・ロールバック保証は[公式ドキュメント](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)を参照した。並行更新の防止はbatchだけで保証せず、既存行の比較更新と組み合わせる。

## 未解決のリスクと検証の限界

- 既にpaidだが有料期間が未反映となったBitcoin決済の自動修復は追加していない。過去データは実際の支払いと照合して運用判断する必要がある。本番データは確認していない。
- R2とD1をまたぐ原子性はない。R2完了後・D1失敗時は追跡を保持して409にする既存設計を維持する。孤立実体・未完了multipartのライフサイクル、恒久失敗候補による掃除の停滞は `storage-lifecycle.md` の既知の課題として残る。
- 1回限定配信の完走判定はサーバーからの送出を根拠とし、ブラウザが復号してディスクに保存したことまでは保証しない。小ファイルの受信後に保存が失敗するケースの完全な救済には別途仕様検討が必要。
- Stripeの順不同イベントによるプランの一時的巻き戻り、カード終端処理と他の課金更新の競合、過去の重複契約は今回修正していない。Bitcoin通知のHMACはcharge IDに対する認証であり、APIでの決済状態の独立照合は行わない既存仕様を維持した。
- 一部の外部通信には明示的な時間制限がない。大容量Blob保存、メモリ内ZIP（上限512MiB）の端末ごとのピークメモリ、圧縮不能なファイルのCPU負荷、同一フォルダ内の大量重複名の探索コストについて、実端末での測定は未実施。
- ZIP内の相対パスは既存仕様を維持している。悪意ある送信者のパスと受信側展開ソフトの組み合わせに関する網羅的検証は行っていない。
- 実環境のWAF、Accessポリシー、レート制限、ログ保存期間、R2 CORS、バックアップ・復元可能性、契約プランごとの上限はコードだけでは保証できない。
- 暗号プリミティブの数学的検証、全ブラウザ・OSの保存動作、本番規模の負荷・CPU・費用測定は監査の保証範囲に含まない。


検証中にコード・テストの追加が並行した実行は最終結果に用いていない。再現段階の全体実行には想定した失敗が含まれ、修正後の競合注入テストにも一度不備が見つかったため、それらを成功扱いにはしていない。上表は修正とテスト注入方法を固定した後の実行結果を示す。
