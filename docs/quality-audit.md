# コード品質監査（2026-10-29）

ファイル転送を中心に5項目を確認した。このPRでは未反映の3項目（本文の読み取り上限、並列通信の中断、例外ログの保護）を修正する。全欠落の検出とHEADの非消費は、PR作成時点のmainで[先行PR #267](https://github.com/ZuikakuGroup/anzdrop/pull/267)により修正済みのため、重複する実装変更を含めていない。新しいサーバー保存情報・依存ライブラリ・データ移行は追加していない。次の改善では、依存関係の更新と、課金・アップロード完了の障害復旧を優先する。

## 調査範囲と方法

`package.json`、Worker設定、CI、既存の設計文書、ソースとテストの配置から構成を確認した。リクエストの振り分けはルーターWorker、画面はAstro SSR / React islands、APIはHono。D1には既存メタデータ、R2には暗号文を保存し、暗号化・復号と鍵の操作はブラウザで行う。Next.js / Cloudflare Pagesへの移行や設定追加は行っていない。

コードの確認はAPI振り分けとセキュリティヘッダー、Access・Cookie・パスワード認証、リカバリー、アップロードのトークン・サイズ制限・完了処理、期限付きダウンロード、暗号化ストリーム、並列通信、保存・ZIP、削除処理、ブログHTMLのサニタイズ、通報・問い合わせの鍵除去、課金Webhookを中心に行った。再現可能な変更にはVitestの回帰テストを追加し、実際のHonoとローカルD1/R2を使う既存テストも実行した。Workersの実装確認には[公式ベストプラクティス](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/)とインストール済みの型定義を参照した。

これは全行の形式検証や侵入テストではない。本番環境の設定・ログ・利用者データは調査していない。既存の公開ページ高速化の未コミット変更は今回の修正に含めず、チェックはそれらが存在する作業ツリーで実行した。

## 修正した問題

重大度はコード上の影響と発生条件からの評価であり、本番障害の発生実績を示すものではない。

| 重大度 | 確認した問題・影響 | 原因と修正 | 対象 |
| --- | --- | --- | --- |
| 高 | 非空ファイルの暗号文が全欠落した場合、空ファイルとして成功する | 空ストリームで期待サイズの照合前にreturnしていた。期待サイズが非ゼロなら復号失敗にする。既存のゼロバイト互換性は維持 | `lib/crypto/stream.ts` |
| 高 | 巨大なアップロード本文が、413になる前にWorkerのメモリを消費する | `request.arrayBuffer()`後にサイズを検証していた。既存の`readBodyWithinLimit`で実測8MiB超過時に読み取りを中断。Content-Lengthの偽装にも対応 | `server/routes/upload/chunk/route.ts` |
| 中 | HEADによるメタデータ確認で回数を消費し、1回限定ファイルの取得を妨げる | HonoのHEADはGETハンドラーを実行する。共有アクセス確認後にHEADを分岐し、R2のheadだけを呼ぶ。本文取得・回数更新・削除を行わない | `server/routes/file/[fileId]/route.ts` |
| 中 | 並列ダウンロードの失敗後も他の取得が継続する。再試行時に不要な応答本文も残る | 失敗時のabortとバッファ解放、再試行前の応答本文cancelを追加。元のエラーがAbortErrorに置き換わらないよう消費側の判定順も修正 | `lib/download/parallelFetch.ts` |
| 中 | 共通API処理が例外に含まれる機密入力をログへ出す可能性がある | 例外値をそのままconsole.errorへ渡していた。既存の認証ハンドラーと同様、固定ルート名だけを記録する。本番での漏洩は未確認 | `lib/api/handler.ts` |

回帰テストは全欠落とゼロバイト互換性、繰り返すHEAD後も1回だけGETできること、並列取得失敗時の他リクエスト中断、再試行時の応答破棄、偽装Content-Length付きの継続ストリームの打ち切り、Error・文字列・オブジェクトの例外値がログに渡らないことを確認する。

## 残存事項と優先順位

### 優先1：依存関係の既知アドバイザリ

当初の監査用作業ツリーで、`npm audit --omit=dev --json`は9パッケージを報告した（high 7、moderate 1、low 1、critical 0）。これは脆弱性の報告件数であり、公開APIで9件の攻撃が成立するという意味ではない。WranglerやViteなどはdependencies経由でも入るため、`--omit=dev`だけでは本番コードに到達するか判断できない。

対象は`@cloudflare/vite-plugin`、`deepmerge`、`miniflare`、`sanitize-html`、`sharp`、`source-map-js`、`undici`、`vite`、`wrangler`。ブログHTML処理が直接利用する`sanitize-html`も含まれる（[GHSA-c9rx-x947-fp3h](https://github.com/advisories/GHSA-c9rx-x947-fp3h)）。実際のブログ入力での再現は未実施。PR作成時点のmainでは、`sanitize-html`は2.18.1へ更新済み（#280）であり、上記件数は最新mainの件数を示さない。自動で依存ツリー全体を更新すると今回の修正と開発環境・ビルド基盤の変更が混ざるため、依存更新は分けて、公開ページ・暗号化転送・ローカル起動を再検証する。

### 優先1：課金反映の途中失敗からの復旧

`server/routes/billing/btc/webhook/route.ts`は支払いをpaidにした後、アカウント期限を別のD1操作で更新する。更新間で失敗すると、再送はalready processedになり、期限延長が行われない経路がコード上にある。本番での発生は未確認。並行する複数支払いにも配慮した原子的な反映と障害注入テストを別途実装する必要がある。今回は課金状態の復旧方針・既存の未反映支払いの扱いを確定していないため変更していない。

### 優先2：アップロード完了の再試行

`server/routes/upload/complete/route.ts`はR2 multipart完了後、filesのINSERTとuploadsの削除を別々に行う。途中失敗時にR2とD1が食い違う可能性があり、既に完了したmultipartをもう一度completeするだけでは復旧できない。操作順は確認済みだが、障害注入による再現は未実施。新しい永続情報を使わず既存のstorage_keyで復旧できるかを検証し、再試行可能な設計を決める。新規永続情報が必要になれば実装前に承認を得る。

### 優先2：外部通信・大容量転送の追加検証

ブログAPIやTurnstileなど、外部fetchに明示的な時間制限がない箇所がある。応答停止時に画面や操作が待ち続ける懸念はあるが、今回障害を再現していない。許容待ち時間と再試行方針を決め、通信停止テストを追加する。モバイル端末でのメモリ使用量、長時間の低速転送、Safari / Firefoxの保存経路も別途計測する。

### 優先3：運用設定と追加のログ監査

WAF、Turnstile設定、Cloudflare Accessポリシー、実環境のキャッシュ挙動はローカルのコード確認だけでは保証できない。共通API以外にも例外をログへ渡す箇所があり、個別にデータの混入可能性を確認する必要がある。今回、実際の機密情報流出や認証突破を確認したわけではない。
